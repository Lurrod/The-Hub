================================================================================
                  BOT DISCORD VALORANT 10MANS - FONCTIONNALITES
================================================================================

Bot Discord pour organiser des parties customs Valorant 5v5 (10mans) avec
2 queues paralleles (Open / Advanced), systeme ELO par queue, formation des
equipes, vote 7/10, verification HenrikDev avec Rating 2.0, ponderation de
l'ELO par la performance, image scoreboard generee par Pillow et leaderboard
en image.

Serveur reserve aux joueurs EU + peak Immortal 1 minimum (>= 2400).
Le bot refuse automatiquement de lier les comptes qui ne respectent pas ce
critere.

Les deux queues sont competitives : chaque match valide donne lieu a une
verification HenrikDev, un calcul de Rating 2.0 par joueur, un ELO pondere
par la performance et une image scoreboard. La seule difference entre les deux
queues est la maniere de former les equipes :

  - Open     : equipes auto-equilibrees selon le PEAK ELO des 6 derniers mois.
  - Advanced : equipes formees par DRAFT DE CAPITAINES + pick/ban de map.


================================================================================
0. INSTALLATION SUR UN SERVEUR
================================================================================

  /setup
    Commande tout-en-un reservee aux admins (manage_guild).
    Cree automatiquement :
      - Categorie "🎮 Valorant 10mans"
      - Salon "leaderboard"        (ou les leaderboards seront postes)
      - Salon "open-queue"         (queue Open)
      - Salon "advanced-queue"     (queue Advanced)
      - Salon "open-results"       (scoreboards de la queue Open)
      - Salon "advanced-results"   (scoreboards de la queue Advanced)
      - Salon "matchs"             (annonces de match)
    Poste immediatement les 2 messages de queue (Open/Advanced) dans leurs
    salons respectifs avec leurs boutons.
    Pre-poste les 2 leaderboards (ignore en silence s'il y a 0 joueur).
    Idempotent : peut etre relance sans risque, ignore tout ce qui existe deja.
    Reponse ephemere visible uniquement par l'admin.

  Categories de match :
    Creees dynamiquement par le bot sous la forme "Match #N" (compteur monotone,
    persiste en MongoDB).
    Supprimees automatiquement en fin de match (vote valide ou annulation admin).
    Chaque categorie contient :
      - Team 1            (vocal)
      - Team 2            (vocal)
      - Waiting Match     (vocal)
      - match-preparation (texte)


================================================================================
1. SYSTEME DE QUEUES (2 EN PARALLELE)
================================================================================

2 queues simultanees, chacune avec son salon + message persistant :

  | Queue    | Salon dedie       | Role requis              | Vocal d'attente        |
  | Open     | #open-queue       | aucun (ouverte a tous)   | Waiting Room Open      |
  | Advanced | #advanced-queue   | Rank Q | Advanced Queue  | Waiting Room Advanced  |

  Verrou single-queue : un joueur ne peut etre que dans UNE queue a la fois.

  /setup-queue queue:<Open|Advanced>
    Place un message persistant avec 2 boutons (Rejoindre / Quitter) dans le
    salon courant. Doit etre lancee dans le salon attendu (open-queue ou
    advanced-queue). Reservee aux administrateurs.
    Si une queue du meme type existe deja, elle est remplacee.
    (Note : /setup le fait automatiquement ; cette commande sert a re-poster
    le message manuellement si besoin.)

  /close-queue queue:<Open|Advanced>
    Retire la queue active du type choisi.
    Retire le role "En Queue" des joueurs qui n'etaient dans aucune autre queue.
    Reservee aux administrateurs.

  Bouton [Rejoindre]
    Le joueur entre dans la queue.
    Deplacement vocal auto vers la "Waiting Room" du type de queue
    (si le joueur est deja dans un salon vocal).
    Attribue le role "En Queue".
    Confirmation EPHEMERE : "✅ Tu as rejoint la queue Open (X/10)" visible
    uniquement par l'utilisateur qui a clique.
    REFUSE si :
      - Pas de compte Riot lie (-> /link-riot d'abord)
      - Deja dans un match en cours (present dans une categorie Match #N active)
      - Deja dans une autre queue (verrou single-queue)
      - Role gate non satisfait (queue Advanced sans "Rank Q | Advanced Queue")
      - Queue pleine (10/10)
      - Queue fermee (match en cours de formation)

  Bouton [Quitter]
    Le joueur quitte la queue.
    Retire le role "En Queue" s'il n'est plus dans aucune autre queue.
    REFUSE s'il n'est pas dans la queue.

  Declenchement auto a 10 joueurs
    Des qu'un 10eme joueur rejoint, le bot ferme la queue de maniere atomique
    (status "forming" via find_one_and_update) et lance la formation du match.

  Persistance complete
    Les 2 vues (Open/Advanced) restent fonctionnelles apres un redemarrage.
    custom_ids distincts : queue_v2:join:open, queue_v2:join:advanced
    (idem pour leave).

  Auto-nettoyage
    Si un joueur quitte le serveur (kick/ban/leave), il est automatiquement
    retire de toutes les queues actives via on_member_remove.


================================================================================
2. LIAISON COMPTE RIOT
================================================================================

  /link-riot riot_id:Pseudo#TAG
    Lie ton compte Discord a ton compte Valorant via l'API HenrikDev.
    Region forcee a EU (pas de parametre region - serveur EU uniquement).

    RESTRICTION : peak Immortal 1+ (effective_elo >= 2400) requis.
      - Si max(peak detecte, MMR actuel) < 2400 -> liaison refusee
      - Le message d'erreur affiche le tier detecte

    Le bot calcule ton "effective ELO" / peak des 6 derniers mois avec la regle :
      - Si ton peak ELO a moins de 6 mois -> on utilise le peak
      - Sinon -> moyenne du MMR sur les 6 derniers mois
      - Si aucun match recent -> fallback sur le peak

    Affiche le rang actuel, l'effective ELO, le peak et la source du calcul.
    Cache 1h pour eviter de spammer l'API HenrikDev.

    Anti multi-comptes : un compte Riot ne peut etre lie qu'a un seul compte
    Discord (puuid unique).

  /unlink-riot
    Supprime la liaison avec ton compte Riot.


================================================================================
3. FORMATION DES EQUIPES
================================================================================

Quand 10 joueurs sont en queue, le bot :

  1. Batch fetch Mongo (2 requetes avec $in) :
       - 10 comptes Riot (riot)
       - 10 docs ELO compound (elo, _id="<uid>:<queue_type>")

  2. Forme les 2 equipes selon le TYPE DE QUEUE (voir 3.1 et 3.2).

  3. Cree dynamiquement une categorie "Match #N" avec match-preparation + Team 1
     + Team 2 + Waiting Match, et applique des permissions directes sur les 10
     joueurs (deny @everyone, allow joueurs + admins + bot).

  4. Persiste le match en base AVANT d'annoncer (message_id=None au depart).
     Si la persistance echoue (Mongo down), aucun message orphelin n'est poste.

  5. Overwrites de permissions EN PARALLELE (asyncio.gather, bucket Discord
     par membre) :
       - Retire "En Queue" des 10 joueurs
       - Applique les overwrites de visibilite sur les 10 joueurs
       - Attribue "Match Host" au lobby leader
     Invariant : permissions posees sur les 10 joueurs AVANT l'envoi du message.

  6. Envoie le message d'annonce dans #match-preparation de la categorie :
       - Mentionne les 10 joueurs (@)
       - Embed avec map, lobby host, compositions, ecart d'equilibrage,
         vocaux a rejoindre, compteur de votes 0/0
       - Boutons "Team A a gagne" / "Team B a gagne" attaches (VoteView)

  7. Voice moves EN PARALLELE (asyncio.gather) :
       Deplace les joueurs vers Team 1 / Team 2 selon l'attribution
       (fallback sur Waiting Match si un vocal d'equipe manque).

  8. Re-poste un nouveau message de queue dans le salon d'origine
     -> la queue est immediatement disponible pour le match suivant.

  Performance : grace a la parallelisation des permissions et des voice moves,
  le temps de formation reste de l'ordre de ~1.5-2 s.


--------------------------------------------------------------------------------
3.1 QUEUE OPEN - AUTO-EQUILIBRAGE PAR PEAK ELO (6 DERNIERS MOIS)
--------------------------------------------------------------------------------

  - Aucun draft : les equipes sont equilibrees automatiquement.
  - Algo BRUTE-FORCE OPTIMAL : itere les 126 partitions 5+5 uniques parmi 10.
  - Metrique d'equilibrage : le PEAK ELO des 6 derniers mois de chaque joueur
    (issu du compte Riot lie via HenrikDev), et non l'ELO serveur accumule.
  - Minimise |sum(team_a) - sum(team_b)|.
    Tie-breakers : ecart des peaks puis ordre des IDs (deterministe).
  - Map tiree au hasard parmi : Haven, Ascent, Split, Sunset, Abyss,
    Lotus, Summit.
  - Lobby leader tire au hasard parmi les 10 joueurs.


--------------------------------------------------------------------------------
3.2 QUEUE ADVANCED - DRAFT DE CAPITAINES + PICK/BAN DE MAP
--------------------------------------------------------------------------------

  Draft de capitaines (services/captain_draft.py)
    - 2 capitaines tires au hasard parmi les 10 joueurs.
    - Les 8 joueurs restants sont draftes a tour de role par les capitaines.
    - Ordre de selection en serpent : A B B A A B B A (equilibre les choix).
    - UI Discord : embed "🎯 Captain Draft" avec equipes en temps reel, pool
      trie par ELO decroissant et marqueur de progression. Un menu deroulant
      (custom_id pro_draft_pick) permet au capitaine courant de choisir ; seul
      le capitaine dont c'est le tour peut l'utiliser.
    - Bouton "Cancel Draft" (admin) : annule le draft, reactive la queue et
      supprime la categorie. Le draft n'a pas de timeout dur.

  Pick / ban de map (services/map_pick_ban.py)
    - Lance apres le draft, sur le pool des 7 maps.
    - 6 bans en alternance A B A B A B -> il reste 1 map.
    - Embed "🗺️ Map Pick & Ban" : maps bannies (barrees, avec emoji du cote
      ayant banni) + maps restantes + marqueur de tour. Menu deroulant
      (custom_id map_ban_pick) reserve au capitaine courant.
    - Choix du cote : le capitaine qui n'a pas fait le dernier ban choisit
      Attack ou Defense (boutons map_side_attack / map_side_defense).
    - Bouton "Cancel ban phase" (admin) : annule, reactive la queue.

  Fallback : si le draft ou le pick/ban est annule par un admin, la queue
  reste active (les joueurs peuvent /quitter puis /rejoindre). Si une erreur
  inattendue survient, le match est annule et la categorie supprimee.


================================================================================
4. SYSTEME DE VOTE
================================================================================

Apres la formation, 2 boutons sont attaches au message du match :

  [Team A a gagne]    [Team B a gagne]

  Regles :
    - SEULS les 10 participants peuvent voter
    - Le vote est modifiable (cliquer A puis B remplace A par B)
    - Si un autre utilisateur clique : refus avec message ephemere
    - Si le match est deja valide / annule / conteste : refuse

  Validation atomique :
    - Des qu'une equipe atteint 7/10 votes (MAJORITY_THRESHOLD) -> validation
    - Transition CAS (pending -> validated_a/b) : un seul vote concurrent peut
      declencher la validation, pas de double application d'ELO
    - L'embed se met a jour en temps reel avec le score des votes
    - La categorie "Match #N" est supprimee automatiquement (claim CAS idempotent)
      -> les joueurs peuvent rejoindre une nouvelle queue sans attendre

  Timeout de 90 minutes (VOTE_TIMEOUT_MINUTES) :
    - Une tache periodique scanne tous les matchs "pending"
    - Si un match depasse 90 min sans atteindre 7/10 -> status "contested"
    - Le bot ping les roles admin (Head Administrators / Administrators / THE HUB)
    - Le score actuel est affiche dans le ping
    - Un admin prend le relais (validation manuelle via /match-force-result
      ou /win + /lose)

  Expiration des contestes :
    - Un match "contested" expire automatiquement apres 24h
      (CONTESTED_EXPIRY_HOURS) pour debloquer les joueurs concernes.


================================================================================
5. VERIFICATION HENRIKDEV + RATING 2.0
================================================================================

Apres validation du vote, l'ELO n'est PAS applique immediatement. Le bot attend
la verification HenrikDev pour recuperer les stats reelles du custom et calculer
un Rating 2.0 par joueur (voir section 7).

  HENRIK_VERIFY_DELAY_MINUTES = 5     # premier essai 5 min apres validation
  HENRIK_VERIFY_TIMEOUT_MINUTES = 30  # abandon a 30 min -> ELO plat

  Boucle de verification (tick periodique) :
    - Pour chaque match valide depuis > 5 min sans ELO applique :
        * Cherche le custom Valorant sur HenrikDev (find_henrik_custom_match)
        * Si trouve -> calcule le Rating 2.0 de chaque joueur, applique l'ELO
          pondere (voir section 6), persiste les stats et poste le scoreboard
        * Si pas trouve -> retry au prochain tick
    - Si depasse 30 min -> applique l'ELO PLAT (gain=20 / perte=20 chacun),
      sans Rating 2.0 ni scoreboard

  Circuit breaker Henrik :
    - HENRIK_CIRCUIT_FAIL_THRESHOLD = 3 echecs consecutifs -> circuit ouvert
    - HENRIK_CIRCUIT_OPEN_MINUTES = 5 min de suspension des appels
    - Evite de saturer les threads et de polluer les logs

  Matchs courts : si le custom compte moins de 6 rounds
  (ELO_MIN_ROUNDS_FOR_WEIGHT), pas de Rating 2.0 -> ELO plat applique (forfaits,
  remakes, etc.).


================================================================================
6. SYSTEME ELO
================================================================================

  ELO_START          = 2000
  ELO_REFERENCE      = 2400 (Immortal 1)
  ELO_BASE_CHANGE    = 20    # base zero-sum
  ELO_WEIGHT_C       = 15    # sensibilite de la ponderation Rating 2.0
  ELO_RATING_BASELINE = 1.0  # ancre (Rating moyen)
  ELO_MIN_ROUNDS_FOR_WEIGHT = 6

  ELO pondere par le Rating 2.0 (les deux queues) :
    Quand HenrikDev a trouve le custom et que le match fait >= 6 rounds, le
    gain/perte de chaque joueur est module par son Rating 2.0 :

      raw = 20 * signe + 15 * (rating - 1.0)

      Victoire -> borne entre +17 (ELO_WIN_MIN) et +26 (ELO_WIN_MAX)
      Defaite  -> borne entre -15 (ELO_LOSS_MIN) et -22 (ELO_LOSS_MAX)

    Exemples (victoire) :
      Rating 1.40 -> +26   (carry, plafonne)
      Rating 1.00 -> +20
      Rating 0.50 -> +17   (plancher)
    Exemples (defaite) :
      Rating 1.40 -> -15   (meilleur perdant, plancher)
      Rating 1.00 -> -20
      Rating 0.50 -> -22   (pire perdant, plafonne)

  ELO plat (fallback) :
    Si le Rating 2.0 est indisponible (Henrik introuvable, match < 6 rounds,
    rating invalide) -> gain = perte = 20 pour tous.

  Plancher : l'ELO d'un perdant ne descend jamais sous 0.
  Compteurs victoires/defaites incrementes automatiquement.

  ELO PAR QUEUE :
    Chaque joueur a 2 ELO independants (un par queue Open/Advanced).
    Compound _id = "<user_id>:<queue_type>" dans la collection elo.
    Premier match dans une queue -> ELO initialise a ELO_START (2000).


================================================================================
7. RATING 2.0
================================================================================

Rating 2.0 est une adaptation du Rating 2.0 (style HLTV) calibree pour
Valorant. Il note la performance d'un joueur sur un match independamment du
resultat. Source : services/rating.py.

  Entrees (par joueur, sur le custom) :
    rounds joues, kills, deaths, assists, degats infliges, rounds KAST.

  Formule (combinaison lineaire calibree, recentree sur ~1.00) :
    rating = INTERCEPT
           + KAST_C * KAST%
           + KPR_C  * (kills / rounds)
           + DPR_C  * (deaths / rounds)
           + IMPACT_C * impact
           + ADR_C  * (degats / rounds)
    avec impact = f(kills/round, assists/round).
    Resultat borne a 0.01 minimum.

  Lecture :
    ~1.00   = joueur moyen
    >= 1.10 = excellente perf (affichee en vert sur le scoreboard)
    < 0.85  = perf faible (affichee en rouge)

  Le Rating 2.0 sert a la fois a ponderer l'ELO (section 6) et a alimenter le
  scoreboard (section 8) et les stats joueur (/stats, section 11).


================================================================================
8. SCOREBOARD (IMAGE)
================================================================================

Quand HenrikDev trouve le custom, le bot genere une image scoreboard (Pillow,
services/scoreboard_img.py) et la poste dans le salon de resultats de la queue :

  - Queue Open     -> #open-results
  - Queue Advanced -> #advanced-results

Si le salon n'existe pas, un warning est logge et rien n'est poste.
Aucun scoreboard si Henrik ne trouve jamais le custom (ELO plat applique).

  Contenu (par joueur, une ligne) :
    NOM | AGENT | R (Rating 2.0) | ELO +/- | ACS | K / D / A | +/- (K-D) |
    KAST | ADR | HS% | FK | FD | +/- (FK-FD)

  Mise en forme :
    - En-tete : Team A (score) | Map | Team B (score)
    - Barre de rounds : un carre par round gagne/perdu par equipe
    - Rating 2.0 colore (vert >= 1.10, rouge < 0.85, sinon blanc)
    - ELO +/- colore (vert si gain, rouge si perte)
    - Barre d'accent verte/rouge selon l'equipe gagnante/perdante

9. COMMANDES ADMIN - MATCH EN COURS
================================================================================

  /match-cancel
    Annule le match en cours dans ce salon (CAS atomique).
    Echoue proprement si un vote concurrent a deja valide / si l'ELO a deja
    ete reclame par la verification.
    Supprime la categorie Match #N et retire le role Match Host des 10 joueurs.
    Retire les boutons de vote du message d'origine.

  /match-cleanup <match_id>
    Supprime de force la categorie Match #N d'un match conteste apres resolution
    manuelle. Reserve aux admins.

  /match-replace quitter:@a remplacant:@b
    Remplace un joueur du match en cours par un autre.
    REFUSE si l'ecart d'ELO entre les deux est > 500 (MAX_REPLACE_ELO_DIFF)
    -> evite de casser l'equilibrage.
    Le remplacant doit avoir un compte Riot lie.

  /match-force-result winner:<A|B>
    Force le resultat d'un match (Team A ou Team B) sans passer par le vote.
    Utile pour resoudre un match conteste. Reserve aux admins.


================================================================================
10. COMMANDES ELO MANUELLES ADMIN (par queue)
================================================================================

Pour les cas ou l'admin enregistre un resultat sans passer par le vote auto
de la queue. TOUTES ces commandes prennent un parametre `queue` (Open/Advanced).

  /win queue: @j1..@j5
    Enregistre une victoire pour 2 a 5 joueurs dans la queue choisie.
    Gain pondere par position de slot : +20 / +18 / +17 / +16 / +15.

  /lose queue: @j1..@j5
    Enregistre une defaite pour 2 a 5 joueurs dans la queue choisie.
    Perte ponderee par position de slot : -10 / -10 / -12 / -13 / -15.
    Plancher a 0.

  /elomodify queue: @joueur action:[add/remove] montant:N
    Ajoute ou retire N points d'ELO a un joueur dans la queue choisie.

  /winmodify queue: @joueur action:[add/remove] montant:N
    Ajoute ou retire N victoires.

  /losemodify queue: @joueur action:[add/remove] montant:N
    Ajoute ou retire N defaites.

  /resetelo queue: joueur:@j  ou  all:True
    Reset l'ELO d'un joueur (ou de tous) a 2000 (ELO_START) dans la queue.

  /reset-queue queue:<Open|Advanced>
    Drop TOUTES les donnees d'une queue (ELO + queue active + matchs).
    Operation irreversible, confirmation requise (bouton, timeout 30s).
    Reservee strictement aux admins (manage_guild, pas de bypass).

Toutes ces commandes sont reservees aux admins (manage_guild) ou au role
configure via /bypass.

11. LEADERBOARD ET STATS
================================================================================

  /leaderboard queue:<Open|Advanced>
    Affiche le classement ELO de la queue choisie sous forme d'image generee
    par leaderboard_img.py (15 joueurs par page, navigation via boutons
    persistants "<" / ">").
    2 leaderboards distincts cohabitent dans #leaderboard (un par queue_type).

    Visibilite :
      - Dans un salon dont le nom contient "leaderboard" -> PUBLIC
      - Dans tout autre salon -> EPHEMERE

  /stats queue:<Open|Advanced> [@joueur]
    Affiche les stats d'un joueur dans la queue choisie, sur 2 pages
    paginees (boutons ◀ / ▶) :
      Page 1 : ELO, rang, winrate, Rating 2.0, K/D/A, KPR/DPR, ADR, HS%,
               KAST, ACS
      Page 2 : multikills, ratio FK/FD, impact, % first kill, repartition
               des tirs (HS / corps / jambes)
    Les stats Rating 2.0 sont alimentees par les matchs verifies par HenrikDev.
    Sans mention -> tes propres stats.

  /inactivity queue:<Open|Advanced>
    Liste les joueurs les plus inactifs de la queue (jusqu'a 25), tries du plus
    inactif au moins inactif d'apres le dernier match joue.
    Format : "Xj Xh Xm" ou "jamais joue".
    Reservee aux admins (ou role bypass).

  Auto-refresh :
    Apres chaque changement d'ELO (vote valide, /win, /lose, /elomodify, etc.),
    le leaderboard de la queue concernee est automatiquement regenere via
    services/leaderboard_refresh.py (debounce per-guild).

15. SYSTEME DE CANDIDATURES
================================================================================

  /welcome
    Poste un message de bienvenue dans le salon "verify" avec un bouton
    persistant "Postuler". Reserve aux admins.

  Bouton [Postuler]
    Ouvre un choix : Joueur ou Coach/Analyst/Manager (Staff).
    Cooldown 1h entre 2 candidatures par utilisateur (CAS atomique).

  Modale Joueur
    Champs : pseudo in-game, lien tracker, tournois/LAN deja faits.
    Postee dans le salon "candidatures" avec boutons Accepter/Refuser.

  Modale Staff
    Champs : nom, poste actuel, experience.
    Postee comme candidature de type staff.

  Bouton [Accepter] (admin)
    Attribue le role "Members" (ou "Coach/Analyst/Manager" pour le staff).
    Renomme le membre avec son pseudo in-game.
    DM de confirmation au candidat. Edite le message pour montrer qui a accepte.

  Bouton [Refuser] (admin)
    Ouvre une modale optionnelle pour la raison.
    Kick le candidat avec la raison, le DM, et edite le message.

  /report
    Poste le panneau de report (bouton persistant) dans le salon courant.
    Cree des salons de tickets (#ticket-N) pour les reclamations.

16. PERSISTANCE MONGODB
================================================================================

Base "elobot". Collections globales (partagees entre guildes) :

  elo
    Classement ELO par joueur ET par queue.
    Compound _id : "<user_id>:<queue_type>" (ex. "1234567890:open")
    {_id, user_id, name, queue_type, elo, wins, losses, last_played}

  riot
    Lien Discord <-> Riot (un doc par user, puuid unique).
    {_id: user_id, riot_name, riot_tag, riot_region, puuid, peak_elo,
     source, fetched_at}

  rules
    Acceptation du reglement (par utilisateur).
    {_id: user_id, accepted_at, display_name}

  matches
    Historique des matchs (toutes guildes).
    {_id: ObjectId, queue_type, origin_guild_id, team_a, team_b, map,
     lobby_leader_id, category_name, category_id, match_number,
     status (pending/validated_a/validated_b/contested), votes, created_at,
     validated_at, message_id, channel_id, elo_applied, elo_applied_at,
     henrik_verified, henrik_found, ...}

  match_player_stats
    Stats par joueur et par match (alimente le scoreboard et les agregats).
    _id : "<match_id>:<user_id>"
    {match_id, user_id, queue_type, map, agent, rounds_played, win,
     kills, deaths, assists, damage_made, damage_received,
     headshots, bodyshots, legshots, multikills_2k/3k/4k/5k,
     first_kills, first_deaths, kast_rounds, acs, rating_2_0, created_at}

  player_rating_aggregates
    Cumuls par joueur et par queue (pour /stats saison).
    _id : "<user_id>:<queue_type>"

19. DEPLOIEMENT (Kimsufi + PM2 + GitHub Actions)
================================================================================

Le bot tourne en production sur un serveur Kimsufi (OVH) via PM2, deploye
automatiquement par GitHub Actions a chaque push sur main.
Voir DEPLOY.md pour la configuration complete (cle SSH, secrets GitHub, etc.).

Variables d'environnement requises (.env, jamais deploye via CI) :
    DISCORD_TOKEN     Token du bot Discord (obligatoire)
    MONGO_URL         URI MongoDB (Atlas ou local) (obligatoire)
    HENRIK_API_KEY    Cle HenrikDev (optionnelle, recommandee en prod)
    LOG_LEVEL         Niveau de log (defaut INFO, optionnel)
    DEV_GUILD_ID      Guilde de sync pour le dev local (optionnel)

Pipeline :
  .github/workflows/ci.yml       ruff + mypy + pytest sur chaque PR + push
  .github/workflows/deploy.yml   push main -> tests -> rsync -> pm2 reload

Commandes PM2 utiles :
    pm2 status
    pm2 logs vrc-bot --lines 100
    pm2 restart vrc-bot
    pm2 restart vrc-bot --update-env    # apres edition du .env
    pm2 monit

Permissions Discord requises pour le bot :
    Voir les salons, Envoyer des messages, Integrer des liens,
    Joindre des fichiers, Gerer les salons (pour /setup),
    Gerer les messages (pour /clear), Deplacer les membres (voice moves),
    Gerer les roles (En Queue, Match Host),
    Gerer les permissions de salon (overwrites par utilisateur pour les
    categories Match #N), Utiliser les commandes slash.
